# demo-real 技术路线（详细版）

本文档用于总结当前 `demo-real` 的完整技术路线，包括架构设计、数据流、协议映射、关键稳定性策略、问题演进与后续优化方向。

## 1. 目标与约束

### 1.1 目标

- 通过 Web 提供比赛级中控大屏展示与实时控制。
- 通过 MCP 提供自然语言 + 工具化控制入口。
- 真实接入 Modbus 设备（十合一传感器 + 执行器）。
- 保证 Web、MCP、设备状态三者一致。

### 1.2 约束

- 现场协议以 `modbus-demo2.py` 为主准，不以通用假设为准。
- 通讯环境可能有抖动、瞬时超时、短时错误读值。
- 需要兼顾“实时性”和“稳定性”，不能只追求高频刷新。

## 2. 架构总览

核心架构采用“三层解耦 + 单状态源”模式：

1. 协议/状态层：`modbus_real_shared.py`
2. 设备桥接层：`modbus_real_runtime.py`
3. 接入层：
- Web API + UI：`web_real_server.py` + `webui/*`
- MCP 工具：`modbus_real_mcp.py`

统一状态源为 `modbus_real_state.json`，Web 与 MCP 都基于该文件读写，避免“每端各算一套状态”。

## 3. 协议落地策略

### 3.1 真实协议映射

按 `modbus-demo2.py` 口径：

- 传感器：`holding 0~9`
- 线圈：`coil 0~3`
- 小灯亮度：默认 `register 7`
- 风扇转速：默认 `register 6`
- 模拟量比例：`raw 0~4095 <-> percent 0~100`

### 3.2 可配置化

为适配现场差异，关键映射均支持环境变量覆盖：

- `MODBUS_AIMO_BRIGHTNESS_REG`
- `MODBUS_AIMO_FAN_REG`
- `MODBUS_AIMO_ANALOG_RAW_MAX`

这使得“改接线/改固件”不需要改代码，只改 `.env`。

## 4. 数据流与控制流

### 4.1 Web 查询流

- 浏览器定时请求 `/api/status`
- `web_real_server.py` 调用 `RealDeviceBridge.get_status_snapshot()`
- bridge 从共享状态返回，或按需刷新设备
- 组装 payload 返回 Web，渲染传感器/执行器/图表

### 4.2 Web 控制流

- 用户点击按钮或拖动滑杆
- 浏览器请求 `/api/control/*`
- server 调用 bridge 对设备写入（coil/register）
- 写入成功后更新共享状态
- 下次 `/api/status` 渲染反映最新结果

### 4.3 MCP 查询与控制流

- MCP 工具入口调用 `modbus_real_mcp.py`
- 工具内部调用 bridge 完成真实写入或状态查询
- 返回结果与 Web 共用同一状态视图结构

## 5. 共享状态设计

状态文件字段分为四类：

- `meta`：版本、更新时间、revision
- `device`：设备地址与协议参数
- `sensor`：在线状态、10 路数据、来源
- `actuators`：线圈、亮度、风扇、来源

关键机制：

- 原子写入（临时文件 + `os.replace`）
- 文件锁（`.lock`）防并发写冲突
- `sensor_revision` / `control_revision` 用于变更跟踪

## 6. 稳定性策略（重点）

### 6.1 写入重试

设备写入采用“失败后重连再试一次”策略：

- `write_coil_with_retry`
- `write_register_with_retry`

目标：降低瞬时断链导致的控制失败。

### 6.2 读回保守更新

执行器读回不再“读失败就写 0”：

- 读取失败时保持最后已知有效值
- 防止状态被错误归零污染

### 6.3 执行器双零防抖

针对现场“偶发双零误读”问题：

- 当历史值非零，却读到 `亮度=0 且 风扇=0` 时
- 立即二次读取确认
- 二次非零：判定首次为瞬时抖动，忽略
- 连续双零：才接受为真实变化

### 6.4 轮询解耦

将传感器读和执行器读写分离锁：

- `sensor_lock` 专管十合一
- `actuator_lock` 专管执行器

效果：避免传感器轮询阻塞控制写入，减少“按钮点了很久才生效”。

### 6.5 避免双轮询争用

默认关闭 MCP 后台轮询：

- `MODBUS_REAL_MCP_ENABLE_POLLER=0`

由 Web 侧作为主要轮询源，MCP 仅在调用时按需刷新。这样可以减少总线争抢和读回抖动。

### 6.6 前端滑杆抗跳动

Web 前端增加滑杆“本地保持窗口”：

- 用户拖动后短时间内，不用后台轮询值覆盖本地滑杆
- 避免出现“刚拖完就跳回”的体验问题

## 7. UI 技术路线

### 7.1 基础形态

- 单页 DataV 风格大屏
- 离线 ECharts（`vendor/echarts.min.js`）
- 网格布局 + KPI + 仪表 + 趋势 + 控制台

### 7.2 状态展示原则

- 传感器：从 `sensor.pretty` 渲染 10 合一卡片
- 执行器：线圈状态 + 亮度/风扇百分比
- 日志：仅保留少量关键事件，避免信息噪声

## 8. MCP 能力路线

当前工具集：

- `modbus_real_get_status`
- `modbus_real_set_coil`
- `modbus_real_set_brightness`
- `modbus_real_set_fan`
- `modbus_real_control`（自然语言分发）

设计重点：

- 显式工具优先，保证可控性
- 自然语言入口作为快捷层
- 控制台输出可追踪每次工具调用

## 9. 配置与部署路线

### 9.1 本地运行

- `.env` 统一管理参数
- `web_real_server.py` 启动 Web + 设备轮询
- `python -m modbus_real_mcp` 启动 MCP 工具服务

### 9.2 网关接入

- `mcp_pipe.py` 读取 `mcp_config.json`
- 默认启用 `local-stdio-modbus-real`
- 通过 `MCP_ENDPOINT` 对接网关 WebSocket

## 10. 演进过程中的关键问题与处理

1. 亮度/风扇映射颠倒
- 根因：现场协议与先验假设不一致
- 处理：切换默认映射并保留 env 可配置

2. 绿灯会自动关闭
- 根因：读回失败被错误覆盖到状态
- 处理：失败不覆盖 + fallback 机制

3. 滑杆自动跳动
- 根因：轮询刷新覆盖用户交互过程
- 处理：前端交互保持窗口 + 后端读回防抖

4. 控制延迟明显
- 根因：传感器与执行器共享锁导致阻塞
- 处理：锁拆分 + 控制通道优先

5. 偶发归零
- 根因：执行器读回偶发双零误读
- 处理：双零二次确认后再决定是否接受

## 11. 可运维性与排障建议

建议长期保留以下日志信息：

- 写入寄存器地址、写入值、重试次数
- 读回寄存器原始值（raw）
- 双零判定路径（首次、二次结果）

推荐新增（可选）：

- `real_io_self_test.py`：一键验证 coil/register 映射
- `diagnostic_mode`：提高日志级别并落文件

## 12. 后续优化路线

1. 引入“命令回执匹配”
- 写入后在短窗口内主动读回并比对
- 达不到阈值时给出明确告警

2. 引入“控制节流策略”
- 滑杆控制按固定频率发送
- 减少总线压力，提高稳定性

3. 引入“状态健康指标”
- 成功率、平均延迟、重连次数
- 为比赛答辩提供可量化指标

4. UI 增加“通信诊断浮层”
- 显示当前寄存器映射、实时轮询周期、最近错误
- 提高现场可解释性

## 13. 总结

`demo-real` 的技术路线核心是：

- 以 `modbus-demo2.py` 为协议单一真源
- 以共享状态文件为跨进程一致性基础
- 以桥接层封装读写与稳定性策略
- 以 Web + MCP 双入口服务比赛展示与交互

当前版本已经具备“可演示、可联调、可扩展”的完整闭环。后续重点在可观测性和自动化自检，以进一步提升现场稳定性。
